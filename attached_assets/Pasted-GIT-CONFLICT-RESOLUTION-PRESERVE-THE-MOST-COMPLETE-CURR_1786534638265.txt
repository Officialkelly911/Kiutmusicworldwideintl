GIT CONFLICT RESOLUTION — PRESERVE THE MOST COMPLETE & CURRENT IMPLEMENTATION

Resolve all active Git merge conflicts in the project and bring the repository back to a clean, consistent, buildable state.

Primary Objective

Review every conflicted file and determine which implementation represents the most recent, complete, improved, and production-ready version.

Do not blindly choose:

* HEAD
* ours
* theirs
* The longest version
* The version with the newest-looking code
* One side of the conflict globally

Instead, evaluate each conflict based on the actual project architecture, recent implementation history, functionality, and approved website requirements.

2. Review Git History

For each conflicted file, inspect the relevant Git history and recent commits.

Use:

* Commit history
* File-specific history
* Recent changes
* Commit timestamps
* Commit messages
* Related files/components
* Dependency relationships

Pay particular attention to the most recent approved implementations and changes made after earlier versions.

The goal is to determine which version contains the latest intended functionality, not merely which version was committed most recently.

⸻

3. Evaluate BOTH SIDES of Every Conflict

For each conflict, compare the competing implementations.

Evaluate:

Functionality

Which version contains the latest working functionality?

Completeness

Which version contains more of the required implementation?

Architecture

Which version better matches the current project architecture?

UI/UX

Which version preserves the latest approved website design?

Performance

Which implementation is more efficient and production-ready?

Responsiveness

Which version preserves the latest desktop, tablet, and mobile behavior?

Accessibility

Which version has the stronger accessibility implementation?

Maintainability

Which implementation better uses existing shared components and avoids duplication?

Integration

Which version correctly integrates with the latest features, APIs, assets, routes, and data structures?

5. Merge Rather Than Replace When Appropriate

If both sides contain valid improvements, merge the functionality intelligently instead of choosing one side and deleting the other.

For example:

If:

HEAD

contains an improved UI implementation and:

incoming

contains newer API functionality, preserve both where they are compatible.

The desired result is:

latest UI + latest functionality + existing architecture

not:

one entire side copied over the other.

simply because one branch no longer references them.

Only remove genuinely obsolete assets when there is clear evidence they are no longer required.

10. Environment Variables and Secrets

Do not commit actual API keys, passwords, tokens, or secrets while resolving conflicts.

Preserve references such as:

MAILCHIMP_API_KEY
MAILCHIMP_SERVER_PREFIX
MAILCHIMP_AUDIENCE_ID
CONTACT_FROM_EMAIL

using the project’s existing environment-variable architecture.

Never hardcode secret credentials into source files.

ACCEPTANCE CRITERIA

The task is complete only when:

1. Every Git conflict has been resolved.
2. Each conflict was evaluated individually.
3. The most recent and most complete implementation has been preserved.
4. Valid improvements from both branches have been merged where appropriate.
5. No approved functionality has been accidentally reverted.
6. No duplicate components or conflicting data structures were introduced.
7. No secrets were exposed or hardcoded.
8. No conflict markers remain.
9. The application builds successfully.
10. Existing tests pass, or any unrelated pre-existing failures are clearly documented.
11. Critical KIUT Music functionality remains operational.
12. The final codebase is consistent, maintainable, and production-ready.

FINAL REPORT

After completion, provide a concise but detailed report containing:

1. Conflicted files identified
2. How each major conflict was resolved
3. Which newer/improved implementation was preserved
4. Where functionality from both branches was merged
5. Any merge-related bugs fixed
6. Build/test results
7. Any remaining issues that existed before the merge
8. Confirmation that no unresolved Git conflicts remain

Do not stop after identifying the conflicts. Resolve, verify, and validate the entire project before reporting completion.
